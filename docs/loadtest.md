## 넘는 곳 — 원인과 고치는 방향 (각 기능 대기 목록에 넣었어요)

1. **민원대장 화면 전환·거르기 풀기·민원 등록·스크롤** (민원대장 세션)
   - 원인: 줄을 전부 그려요(3년치 1,548줄 = DOM 9.6만 개). 화면을 열 때, "전체"로 되돌릴 때, 등록해서 목록이 바뀔 때마다 전부 다시 그려요.
   - 1안 **필요한 만큼만 그리기**(보이는 줄 + 앞뒤 몇 줄, 스크롤하면 바꿔 그림) — 줄 높이가 제각각이라 높이를 재 두는 방식. ← 권해요: 자료가 늘어도 빠르기가 그대로예요.
   - 2안 나눠 그리기(처음 100줄, 아래로 내리면 100줄씩 더) — 만들기 쉽지만 끝까지 내리면 다시 무거워져요.
2. **업무일지 전체 검색** (업무일지 세션)
   - 원인: 맞는 기록을 전부 한 번에 그려요("배수" 3년치 711일·1,630건 = DOM 4.8만 개). 글자를 칠 때마다 다시 찾고 다시 그려요.
   - 1안 **결과는 최근 날짜부터 30일씩 그리기**(아래로 내리면 더) + 치는 동안 0.15초 기다렸다 찾기. ← 권해요: 화면 쪽만 고치면 돼요.
   - 2안 검색을 core에서(SQLite 전문 검색) 하고 날짜 묶음 단위로 받아 오기 — 잠금 풀 때 업무일지 전체를 읽지 않아도 돼서 첫 화면도 가벼워지지만 일이 커요.
3. **할 일 화면 전환(3년치)** (할 일 세션)
   - 원인: 목록을 묶을 때 할 일마다 전체 할 일을 다시 훑어 하위 항목을 찾아요(`tasks.ts` 73~74행, 5,937건이면 약 3,500만 번). DOM은 2천 개로 작아요 — 그리기가 아니라 계산이에요.
   - 1안 **위 항목 번호로 한 번 묶어 두기**(Map) — 몇 줄 고치면 수 ms로 줄어요. ← 권해요.
   - 2안 오래된 완료 할 일은 읽지 않기(core가 30일 지난 완료는 빼고 줌) — 구글 맞추기(`desiredTasks` 3년치 60ms)도 함께 가벼워져요.
4. **탐색기 화면 전환(파일 2,000개 폴더)** (탐색기 세션)
   - 원인: 두 창 모두 파일을 전부 그려요(2,000개 × 2창 = 줄 4,000개·아이콘 4,000개, DOM 4만 개).
   - 1안 **필요한 만큼만 그리기**(목록 줄 높이가 같아 쉬워요). ← 권해요.
   - 2안 아이콘을 줄마다 그리지 않고 확장자별 그림 하나를 같이 쓰기 — 절반쯤 줄지만 2,000개를 넘는 폴더는 여전히 느려요.
5. **엑셀 쓰기 경고**(작게): 내보낼 때마다 `Theme color '10' must be in the the range 0 - 9`가 찍혀요 — 서식 색 하나가 빠지고 있을 수 있어요(민원대장 세션, 엑셀).

통과한 곳: 첫 화면, 업무일지·캘린더·연락처·민원처리 전환, 날짜·달 넘기기, 이름 검색·민원대장·할 일·탐색기 필터 검색. 다만 첫 화면 360ms 중 전체 읽기가 130ms라 5년 넘게 쌓이면 2번의 2안(읽기 나누기)을 다시 봐요.

## 재는 방법

### 리눅스 작업 공간 (Claude가 함)
- **core(Rust)**: `tools/load/src/bench.rs` — 실제 SQLCipher 파일을 core로 열어(`Store::open`, Argon2 포함) 화면별 읽기, 잠금 풀 때 읽는 것 전부(+JSON 만들기), 민원·업무일지 저장 한 번(사본에), 엑셀 쓰기.
- **화면**: 미리 보기(앱 화면 코드 그대로, 저장만 메모리 흉내) + Playwright. 누른 순간(`performance.now`)부터 화면이 마지막으로 바뀐 뒤 첫 프레임까지. 스크롤은 프레임마다 40px씩 3초 내리며 프레임 간격으로 fps.
- **앱에서 걸릴 시간(추정)** = 화면 값 + 그 화면이 부르는 core 읽기. 첫 화면은 열기 + 전체 읽기(+JSON) + 화면 그리기.
- 다시 재기: `tools/load/README.md`.

### 윈도우 (사용자 시험)
**A. 3년치 자료 파일 열어 보기** — 파일 바꿔 넣기(권해요). 설정의 "폴더 바꾸기"는 지금 자료를 그 폴더로 **옮겨 버리고**, "백업 불러오기"는 지금 자료를 **덮어써서** 이번 시험엔 쓰지 않아요.
1. 트레이의 기Log 아이콘 우클릭 → "끝내기".
2. `문서\giLog` 폴더 이름을 `giLog_원본`으로 바꿔요(진짜 자료는 그대로 보관).
3. 새 `문서\giLog` 폴더를 만들고, 받은 `gilog_3년치.zip`을 풀어 `gilog.db`·`gilog.key.json` 두 파일을 넣어요(둘 다 있어야 열려요).
4. 기Log를 켜고 암호 `test` → Enter를 누른 순간부터 업무일지가 다 보일 때까지 초시계로 재요(3번).
5. 민원대장·탐색기·할 일로 옮겨 다니며 느린 곳, 민원대장 스크롤이 끊기는지 봐요.
6. 끝나면 1번처럼 끝내고, `문서\giLog`(시험 폴더)를 지우고 `giLog_원본` 이름을 `giLog`로 되돌려요. 다시 켤 때 암호를 한 번 물을 수 있어요(진짜 암호로 열면 돼요).

**B. 메모리** (A의 3년치 파일로)
1. 기Log를 켜고 잠금을 풀어요.
2. 10분 동안 그대로 두어요.
3. Ctrl+Shift+Esc → 작업 관리자 → "프로세스" 탭.
4. "앱"의 **기Log**(giLog) 줄 왼쪽 ›를 눌러 펼쳐요 — 안의 Microsoft Edge WebView2 줄들까지 합친 값이 접힌 줄의 "메모리" 칸이에요. 그 값을 적어요(①).
5. 사이드바에서 탐색기·민원대장·민원처리·캘린더·할 일·업무일지·업무연락처를 차례로 한 번씩 눌러요.
6. 마지막 화면이 다 그려지면 4번의 값을 다시 적어요(②). 기준: ①·② 모두 250MB 아래.

**C. 업무일지 인쇄 미리 보기(1년)**: 업무일지 → 인쇄 → 시작일 `20251018`·끝일 `20261017` → 인쇄 → 엣지 인쇄 창이 다 뜰 때까지 초시계(350쪽). 작업 공간에서는 엣지 인쇄 창이 뜨기 직전까지만 잴 수 있어요.
